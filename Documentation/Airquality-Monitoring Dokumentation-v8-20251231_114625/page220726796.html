Frontend - MK

1. Motivation

 Ein reaktives Web-UI, das Messwerte übersichtlich darstellt, Sessions bedienbar macht und Ventilator/Diffusor per Klick steuert und die Daten exportierbar macht(z.B. als pdf) – optional auch ohne laufendes Backend (Mock-Modus).

2. Gesamtübersicht (Frontend-intern)

Technologie-Stack

  • Framework: React (mit Hooks), Vite als Build-Tool

  • Styling: Tailwind CSS

  • HTTP/WebSocket: Axios (REST), WebSocket 

  • Tests: Jest + React Testing Library

Frontend-Architektur

src/
├─ components/        -> UI-Bausteine (z.B. DeviceControlPanel, SessionManager)
├─ services/          -> API-Zugriff (fetchDeviceStatus, fetchSessions, ...)
├─ hooks/             -> Wiederverwendbare Logik (z.B. useLiveStream, useSessionDelta)
├─ utils/             -> Hilfsfunktionen (Export, Env-Shim)
└─ ...

  • services kapseln alle Backend-Aufrufe → leicht zu mocken.

  • components sind primär zustandsarm, beziehen Daten über Hooks/Services.

  • tests spiegeln die Ordnerstruktur wider und testen Komponenten & Services isoliert.

Zusammenspiel

  1. Komponente mountet → ruft Service-Funktion(en) aus src/services/api.

  2. Daten kommen (Mock/Backend) → State aktualisiert → UI rendert.

  3. User-Aktionen (Buttons) lösen Service-Calls aus → State-Update.

3. Wichtige Abläufe

3.1 Gerätesteuerung (Ventilator/Diffusor)

Sequenz :

  1. DeviceControlPanel mounted → setTimeout(loadStatus, 1000)

  2. loadStatus() ruft fetchDeviceStatus()

  3. UI zeigt Status-Badges & Buttons. Klick auf „An/Aus/Auto“ → controlVentilator|controlDiffusor()

  4. Busy-Flag (loadingKey) deaktiviert Button kurz; nach Response wird Status aktualisiert.

3.2 Session-Verwaltung

  1. SessionManager lädt Sessions via fetchSessions()

  2. Start/Ende via startSession() / endSession()

  3. Datenexport in exportSessionData() (CSV/JSON) über Blob/Download-Link.

3.3 Live-Daten (falls genutzt)

  1. Hook useLiveStream öffnet WebSocket oder Polling zu /live-data

  2. State wird fortlaufend aktualisiert → Charts/Badges updaten sich.

5. Installation / Einrichtung

npm install        # Dependencies
npm run dev        # Dev-Server starten

Öffne die ausgegebene URL (z. B. http://localhost:5173).

ENV-Konfiguration

VITE_USE_MOCK=true              # Mock-Daten einschalten
VITE_API_URL=http://localhost:8000   # Backend-URL im Echtbetrieb
VITE_WS_URL=ws://172.20.10.4:8000
Bzw. Starten des Docker compose (siehe Deployment Dokumentation)
Über Docker Container auch Zugriff von anderen Geräten auf das Frontend über (172.20.10.4:3000) aufrufbar (PI broadcasted im Browser)
 

6. Tests & Qualitätssicherung

npm run test          # Jest im Watch-Modus
npm run test:once     # einmalig (CI)

  • Komponenten-Tests mit React Testing Library

  • Fake-Timer bei Komponenten, die setTimeout nutzen (z. B. DeviceControlPanel)

  • API-Funktionen werden über jest.mock('src/services/api') isoliert.

7. Architekturelle Entscheidungen (Frontend)

  • React + Vite: schnelle Dev-Experience, Hot Module Reloading

  • Tailwind CSS: schnelle UI-Prototypen, konsistente Utility-Klassen

  • Mock-Modus per ENV statt Hardcoding → flexibles Testen/Demo

8. Betriebshinweise

  • Frontend ist ein statisches Bundle (npm run build → dist/) und kann auf jedem Static Host laufen (Netlify, Vercel, Nginx).

  • ENV-Variablen müssen zur Build-Zeit gesetzt sein (Vite liest .env*).

  • Keine regelmäßigen Wartungsaufgaben nötig (keine Serverprozesse).


9. Detailierte Frontend-Implementierung

9.1 Services (src/services/api.js)

Rolle: zentrale Abstraktionsschicht für REST- und WebSocket-Kommunikation + Mocking.

  • ENV-Schalter: USE_MOCK entscheidet, ob echte Endpunkte oder Mock-Funktionen genutzt werden.

  • Axios-Client mit Retry & Interceptor:

export const http = axios.create({ baseURL: BASE_URL, timeout: 8000 });
axiosRetry(http, { retries: 2, retryDelay: axiosRetry.exponentialDelay, retryCondition: err => axiosRetry.isNetworkError(err) || err.code === 'ECONNABORTED' });
http.interceptors.response.use(res => res, err => { console.warn('[HTTP INTERCEPTOR]', err.config?.url, err.message); return Promise.reject(err); });

  • Mock-Helfer & Normalizer: Zufallswerte (rand), Key-Normalisierung (PM2_5 → PM2.5) und normalizeLivePayload sorgen für einheitliche Datenstrukturen.

  • Sessions/History/Devices: CRUD-ähnliche Funktionen (fetchSessions, startSession, fetchSessionData, controlVentilator, …) sind klar getrennt.

  • WebSocket-Handling (connectLive) mit automatischem Reconnect (bis zu 6 Versuche) und Mock-Interval im Demo-Modus.

9.2 Hooks

useLiveStream(active)

  • Lädt initial per HTTP (fetchLiveData) und hält danach via connectLive den State aktuell.

  • Rückgabe: { live, wsState } – Komponenten müssen nur diese Werte konsumieren.

useEffect(() => {
  if (!active) return;
  fetchLiveData().then(first => mounted && setLive(first));
  cleanupRef.current = connectLive(payload => mounted && setLive(payload), setWsState);
  return () => cleanupRef.current?.();
}, [active]);

useSessionDelta(sessionId, enabled, pollingMs)

  • Lädt initial komplette History (fetchSessionData) und pollt danach deltas via fetchSessionDataSince.

  • Nutzt setInterval → im Test werden Fake-Timer eingesetzt.

9.4 Utilities

  • exportSessionData(rows, format) → CSV/JSON Export via Blob/URL.

  • envShim.js → Fallback für ENV im Testumfeld; kann durch direktes Mocken von import.meta.env ersetzt werden.

9.5 Tests

  • Komponenten-Tests (RTL): z. B. DeviceControlPanel.test.jsx mit Fake-Timern.

  • Hook-Tests (renderHook): useLiveStream, useSessionDelta → prüfen initiale Ladung & Updates.

  • Service-Tests: API-Methoden werden komplett gemockt → Struktur & Rückgabewerte werden verifiziert.

// Fake-Timer Beispiel
beforeAll(() => jest.useFakeTimers());
afterAll(() => jest.useRealTimers());
await act(async () => { jest.advanceTimersByTime(1000); await Promise.resolve(); });

9.6 ENV & Mocking-Strategie

  • .env steuert Modus & URLs: VITE_USE_MOCK, VITE_API_URL, VITE_WS_URL.

  • Im Mock-Modus liefern Services synthetische, aber realistisch variierende Daten.

  • Vorteil: Frontend ist vollständig demonstrierbar ohne Backend/Hardware.

9.7 Styling & UI-Konzept

  • Tailwind CSS + eigene Utility-Klassen (z. B. .aq-card, .badge).

  • Heller Hintergrund mit CSS-Gradients, konsistente Komponentenkarten.

  • Kleine, konsistente Typografieklassen (text-xxs).

9.8  Router & Entry-Point

  • App.jsx nutzt React Router (/dashboard).

  • main.jsx setzt window.__VITE_ENV__ (Debugging) und rendert <App /> in #root.
