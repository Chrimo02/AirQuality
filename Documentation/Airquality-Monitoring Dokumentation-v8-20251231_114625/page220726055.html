Session-Management im Code - PP

1. Session-Beginn und -Beendigung (API-Workflow)

Das Projekt unterstützt ein vollautomatisiertes Session-Management, sowohl für die Kommandozeile als auch über die REST-API (z. B. für das Web-Frontend).

Start einer Session

  • Per API (POST /sessions):

    • Der User (CLI oder Frontend) gibt einen eindeutigen Session-Namen, optional einen Ort, sowie den Typ („indoor“ oder „outdoor“) an.

    • Die Funktion start_session() prüft, ob schon eine offene Session mit diesem Namen existiert:

      • Falls ja: Die vorhandene Session wird weiterverwendet, Messwerte werden angehängt.

      • Falls nein: Eine neue Session wird mit aktuellem Startzeitpunkt, Name, Ort, Typ angelegt und als aktiv markiert.

    • Die aktuell aktive Session-ID wird global gemerkt (current_session_id), sodass alle Messwerte automatisch korrekt zugeordnet werden.

  • Typischer Aufruf (CLI oder API):

    # Beispiel (Frontend oder automatisiert)
POST /sessions
{
    "name": "Wohnzimmer Abend",
    "location": "EG",
    "session_type": "indoor"
}


    (Im CLI-Workflow wäre es äquivalent zu:)

  •  python main.py -s "Wohnzimmer Abend" -l "EG" --type indoor

Beenden einer Session

  • Per API (PUT /sessions/{session_id}/end):

    • Die Funktion end_session() trägt den Endzeitpunkt in die Datenbank ein.

    • Die Session ist damit geschlossen und kann nicht erneut fortgeführt werden.

    • Nach dem Beenden wird current_session_id wieder auf None gesetzt.

Session-Fortsetzung und Duplikatvermeidung

  • Wird versucht, eine Session mit gleichem Namen neu zu starten, prüft die Datenbanklogik, ob bereits eine aktive (nicht beendete) Session existiert:

    • Falls ja: Die Messwerte werden weiterhin unter dieser Session-ID gespeichert.

    • Falls nein: Es wird eine neue Session mit diesem Namen angelegt.

2. Vorteile der Session-Verwaltung

  • Daten werden immer eindeutig zugeordnet und bleiben gruppierbar (z. B. alle Messwerte im "Wohnzimmer" lassen sich gemeinsam auswerten).

  • Sessionnamen sind eindeutig (UNIQUE-Constraint) – ein versehentliches doppeltes Anlegen wird unterbunden.

  • Jeder Session kann ein Ort (location) und Typ (indoor/outdoor) zugewiesen werden.

  • Bequeme Weiterverarbeitung: Die Session-ID wird für jeden Messwert automatisch mitgespeichert.

3. Beispiele aus dem Code

Start einer Session (API):

@app.post("/sessions", response_model=SessionResponse)
async def create_session(session: SessionCreate):
    global current_session_id
    conn = get_db_connection()
    session_id = start_session(
        conn, 
        session.name, 
        session.location, 
        session.session_type
    )
    current_session_id = session_id
    ...


Session-Ende (API):

@app.put("/sessions/{session_id}/end")
async def end_session_endpoint(session_id: int):
    global current_session_id
    conn = get_db_connection()
    end_session(conn, session_id)
    if current_session_id == session_id:
        current_session_id = None
    ...


Zusammengefasst:

  • Das Session-Management sorgt für klare Datentrennung, verhindert Namensdopplungen und ermöglicht eine lückenlose Messhistorie.

  • Sessions können bequem per API oder CLI gestartet und beendet werden – ein automatisiertes Handling aller Zuordnungen ist gewährleistet.
