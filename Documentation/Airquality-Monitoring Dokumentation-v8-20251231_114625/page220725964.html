Datenbank-Design & Implementierung - PP

1. Was sind „Sessions“? – Konzept und Nutzen

Sessions bezeichnen im Projekt jeweils einen definierten Zeitraum, in dem eine zusammenhängende Messreihe stattfindet.
Eine Session bündelt alle Messwerte, die zu einer bestimmten Umgebung, einem bestimmten Raum, Experiment oder Testablauf gehören.

Hintergrund und Motivation:

  • Sensoren werden oft an unterschiedlichen Orten (z. B. Wohnzimmer, Schlafzimmer, Außenbereich) oder für verschiedene Experimente verwendet.

  • Ohne Sessions wären alle Messwerte in der Datenbank nicht eindeutig zuordenbar – eine Auswertung nach Ort, Zeitraum oder Test würde unmöglich bzw. sehr aufwendig.

Eine Session umfasst immer:

  • Name: Klar zuordnungsbare Bezeichnung (z. B. „Wohnzimmer-Abend“, „Outdoor-Test Juli“)

  • Location: Optional – genauere Beschreibung des Standorts

  • Session-Typ: Steuert, ob das Indoor- oder Outdoor-Regelwerk zur Bewertung verwendet wird

  • Start- und End-Zeitpunkt: Automatisch durch das Skript gesetzt, um den Zeitbereich der Messung eindeutig abzubilden

  • Verknüpfte Messwerte: Alle Luftdaten (Feinstaub, Temperatur, etc.), die während der Session erfasst werden

Ablauf im System:

  • Beim Start einer neuen Messung gibt der Nutzer Name, Ort und Typ an (z. B. per CLI-Parameter).

  • Das Skript legt (wenn nötig) eine neue Session in der Datenbank an und merkt sich die ID.

  • Alle im weiteren Verlauf eingelesenen Sensorwerte werden dieser Session-ID zugeordnet.

  • Am Ende der Messung wird die Session per Zeitstempel abgeschlossen.

Vorteile des Session-Konzepts:

  • Messdaten bleiben immer klar gruppiert und nachvollziehbar (z. B. für Reports, Diagramme, Export)

  • Parallele oder aufeinanderfolgende Versuchsreihen können sauber unterschieden werden

  • Session-Management verhindert doppelte Namen und damit Datenchaos in der Datenbank

2. Aufbau und Tabellenstruktur

Das Projekt nutzt eine SQLite-Datenbank (air_quality.db) im Unterordner database/.
Die Datenbank besteht aus zwei logisch verknüpften Tabellen:

sessions

Speichert Metadaten zu einzelnen Mess-Sessions.

  • id (INTEGER, PRIMARY KEY, AUTOINCREMENT): Eindeutige Session-ID

  • name (TEXT, UNIQUE, NOT NULL): Bezeichnung der Messreihe (muss eindeutig sein)

  • location (TEXT): Optionaler Ortsname (z.B. "Wohnzimmer", "Labor")

  • start_time (TEXT, NOT NULL): Zeitstempel beim Start der Session

  • end_time (TEXT): Zeitstempel beim Beenden der Session

  • session_type (TEXT, NOT NULL): "indoor" oder "outdoor" für das Regelwerk

air_data

Speichert alle ausgelesenen Messdaten und referenziert immer eine Session.

  • id (INTEGER, PRIMARY KEY, AUTOINCREMENT): Eindeutige Messwert-ID

  • timestamp (TEXT, NOT NULL): Zeitpunkt der Messung

  • pm1_0, pm2_5, pm10 (REAL): Feinstaubwerte aus der Messzeile

  • raw_line (TEXT): Die vollständige, rohe Sensorzeile (zur späteren Analyse)

  • session_id (INTEGER, NOT NULL): Fremdschlüssel auf sessions.id

# CREATE TABLE Beispiel aus db_helper.py
c.execute('''
    CREATE TABLE IF NOT EXISTS sessions (
        id            INTEGER PRIMARY KEY AUTOINCREMENT,
        name          TEXT    NOT NULL UNIQUE,
        location      TEXT,
        start_time    TEXT    NOT NULL,
        end_time      TEXT,
        session_type  TEXT    NOT NULL
    );
''')
c.execute('''
    CREATE TABLE IF NOT EXISTS air_data (
        id          INTEGER PRIMARY KEY AUTOINCREMENT,
        timestamp   TEXT    NOT NULL,
        pm1_0       REAL,
        pm2_5       REAL,
        pm10        REAL,
        raw_line    TEXT,
        session_id  INTEGER NOT NULL,
        FOREIGN KEY(session_id) REFERENCES sessions(id)
    );
''')



3. Beziehungen und Regeln

  • Eindeutige Sessionnamen:
    Jede Session hat einen eindeutigen Namen (UNIQUE).
    Ein erneuter Start mit gleichem Namen führt dazu, dass Messwerte der selben Session-ID zugeordnet werden.

  • Session-Typ:
    "indoor" oder "outdoor" steuert das Bewertungsregelwerk.

  • Fremdschlüssel:
    Messwerte sind immer einer Session zugeordnet (session_id als FOREIGN KEY).

4. Datenhaltung und Insert-Logik

Session-Handling:

  • Neue Session wird über start_session angelegt:

    • Prüft, ob der Name schon existiert; falls ja, wird die Session-ID zurückgegeben.

    • Legt sonst eine neue Session an.

  • Beenden einer Session (end_session) trägt einen Endzeitpunkt ein.

Messwert-Speicherung:

  • Über insert_data werden Messwerte mit Zeitstempel, extrahierten PM-Werten und der kompletten Rohzeile in air_data gespeichert.

  • Jeder Datensatz bekommt den zugehörigen session_id.

5. Fehlerbehandlung und Migration

  • Fehlerbehandlung:
    Jeder Datenbankzugriff ist mit try/except abgesichert. Fehler werden auf der Konsole protokolliert.

  • Schema-Änderungen/Migration:
    Bei Änderungen an den Tabellen (z. B. neue Spalten wie session_type) wird empfohlen, die alte Datenbankdatei zu löschen – beim nächsten Start legen die Python-Skripte die DB automatisch neu mit aktuellem Schema an.

6. Visualisierung 

Zusammengefasst:

  • Die SQLite-Datenbank ist übersichtlich, modular und schützt vor Redundanzen (z. B. durch UNIQUE-Constraint auf name).

  • Messdaten und Sessions sind sauber voneinander getrennt und durch einen Fremdschlüssel verknüpft.

  • Die Einbindung neuer Felder (wie weitere Sensorkanäle) ist leicht erweiterbar.
