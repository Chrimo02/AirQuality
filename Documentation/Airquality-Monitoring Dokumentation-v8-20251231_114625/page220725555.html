Teststrategie und Testausführung - CM

Ziel der Tests

Im Projekt werden Unit-Tests eingesetzt, um zentrale Anwendungslogik wie AirQuality-Parsing, Farbberechnung und andere reine Software-Funktionen unabhängig von der Hardware automatisiert zu prüfen. Dadurch können Fehler frühzeitig erkannt und die Wartbarkeit des Projekts verbessert werden.


Testansatz

Es wird zwischen zwei Kategorien von Code unterschieden:

1. Logikfunktionen ohne Hardwarebezug

  • Beispiele: AirQuality-Parsing, Farbberechnungen, Interpolationen

  • Test: Diese Funktionen sind unabhängig von der ESP32-Hardware und werden direkt auf dem PC getestet (“Host Testing”).

2. Hardwareabhängige Komponenten

  • Beispiele: Ansteuerung des NeoPixel-Rings, MQTT-Kommunikation, WLAN-Handling

  • Test: Für diese Bereiche sind klassische Unit-Tests nur eingeschränkt sinnvoll, da sie Hardwarezugriffe erfordern. Sie werden daher durch gezielte manuelle Tests am Gerät überprüft.

Konkrete Teststrategie

  • Alle Unit-Tests werden als eigenständiges, plattformunabhängiges C++-Testfile entwickelt und auf dem PC ausgeführt.

  • Catch2 wird als Framework für einfache, leicht lesbare Unit-Tests verwendet. Die Tests sind unabhängig von Arduino- oder ESP32-spezifischen Bibliotheken und laufen schnell lokal oder in der CI/CD.

  • Die Testfälle werden in einer Datei (z.B. test_logic.cpp) zentral verwaltet.

  • Das Testfile enthält umfassende Tests für alle Kernfunktionen der Logik, z.B.:

    • parseAirQuality: Robustheit gegenüber Groß-/Kleinschreibung, Whitespace, ungültigen Eingaben.

    • safeColor: Korrekte Begrenzung von Farbwerten außerhalb des erlaubten Bereichs.

    • interpolate: Richtiges Interpolieren von Farbwerten bei unterschiedlichen Start- und Zielwerten.


Begründung für diesen Ansatz

  • Schnelle Ausführung: Tests laufen in Sekundenbruchteilen auf dem PC, unabhängig von Embedded-Hardware.

  • Einfache Integration: Alle Teammitglieder können die Tests ausführen, ohne spezielle Hardware zu benötigen.

  • Klares Feedback: Fehler in der Logik werden sofort erkannt, Refactorings sind risikofrei möglich.

  • Portabilität: Die Teststrategie ist unabhängig vom Betriebssystem oder der späteren Hardware.


Ergänzende Testmaßnahmen

Die Überprüfung der Hardware-Funktionen (z.B. LED-Ansteuerung, MQTT-Verbindung) erfolgt durch gezielte manuelle Tests am ESP32, wie z.B. durch Senden von Farbbefehlen und Beobachtung der tatsächlichen LED-Reaktionen.


Beispielhafter Testablauf

  1. Code-Änderung an einer Logikfunktion (z.B. AirQuality-Parsing).

  2. Ausführung der Unit-Tests am PC (./test_logic).

  3. Feedback: Es wird sofort angezeigt, ob alle Tests bestanden wurden.

  4. Integration: Anschließend erfolgt die Integration auf dem ESP32 und die manuelle Prüfung der Hardwarefunktionen.

Anleitung: Ausführung der Unit-Tests auf dem PC

Voraussetzungen

  • C++ Compiler (z.B. g++, clang, MSVC)

  • Catch2 Test-Framework (nur .hpp nötig) → Ist beim Klonen unseres Repositories bereits im ESP32-Test-Directory enthalten

Schritte:

  1. Catch2 herunterladen (falls nicht schon vorhanden)
    Die aktuelle Catch2 Single-Header-Datei hier herunterladen und im selben Verzeichnis wie die Testdatei (test_logic.cpp) absichern.

  2. Testdatei ablegen
    Die Datei test_logic.cpp ins gleiche Verzeichnis.

  3. Kompilieren

    g++ -std=c++17 -o test_logic test_logic.cpp

    (Alternativ: clang++ -std=c++17 -o test_logic test_logic.cpp)

  4. Tests ausführen
    ./test_logic
  5. Ergebnis
    Es erscheint eine Übersicht aller Testfälle mit Angabe von "passed"/"failed".

Hinweis:

Falls der Fehler 'catch.hpp' file not found auftritt, muss erneut überprüft und sichergestellt werden, dass sich die Datei catch.hpp im gleichen Verzeichnis wie test_logic.cpp befindet und im Testfile der Include mit #include "catch.hpp" erfolgt.
